# Implementation Plan

- [ ] 1. 交渉チャット機能の基盤を整備する
- [ ] 1.1 LLMオプション機能の設定と依存を導入する
  - LangChainを利用するための依存関係を追加し、サーバ側でのみLLM実行できる前提を整える
  - 実行環境でLLMが利用できない場合に備えて、既定でLLMを無効にできる設定を用意する
  - LLMの有効/無効を切り替えるための最小設定（環境変数、既定値、ガード）を定義する
  - _Requirements: 3.1_

- [ ] 1.2 LangChainのバージョンをリポジトリ上で明確に確認できるようにする
  - 依存の固定方針を適用し、実行時に参照されるLangChain関連パッケージのバージョンを確認できる状態にする
  - バージョン確認を1コマンドで実行できるようにし、アップデート時に差分確認しやすくする
  - _Requirements: 6.1_

- [ ] 1.3 MCP参照運用を支援する開発用チェックを追加する
  - Docs by LangChain MCP の参照経路が有効であることを、開発時に検証できるようにする
  - 互換性問題が起きた際に、影響範囲を特定するためのチェック項目を実行可能な形で残す
  - _Requirements: 6.2, 6.3_

- [ ] 2. 交渉セッションの永続化と整合性を実装する
- [ ] 2.1 交渉セッションとメッセージの永続化を追加する
  - 交渉セッションと会話メッセージを保存できるデータモデルを追加する
  - セッションとメッセージの関連、取得順序、最低限の検索/参照に必要な制約を定義する
  - _Requirements: 2.1, 2.2, 4.3_

- [ ] 2.2 交渉ステータス（進行中/合意/決裂）を永続化する
  - 交渉が進行中か確定済みかを一貫して判定できる状態を持つ
  - 合意/決裂へ遷移した後は状態が変わらないことを保証する
  - _Requirements: 2.3, 2.4, 2.5_

- [ ] 2.3 交渉セッション単位の要約ログを保存できるようにする
  - 交渉ターンごとの入出力を要約として追跡できる永続化手段を追加する
  - LLM利用有無と失敗理由などの最小メタデータを保存できるようにする
  - _Requirements: 7.1_

- [ ] 3. ドメインサービスを実装する
- [ ] 3.1 交渉セッションの作成・取得・追記・確定を扱えるサービスを実装する
  - セッション作成、直近履歴取得、ユーザー/選手メッセージ追記、合意/決裂確定の振る舞いを実装する
  - 確定済みセッションへの追記を拒否し、理由を返せるようにする
  - _Requirements: 2.1, 2.2, 2.3, 2.4, 2.5_

- [ ] 3.2 (P) 選手コンテキストを提供するサービスを実装する
  - 交渉開始/返答生成に必要な選手の基本情報を取得できるようにする
  - 契約関連情報を取得し、交渉に適した要約コンテキストを組み立てる
  - 情報取得に失敗した場合も、最小限の情報で交渉を継続できるようにする
  - _Requirements: 5.1, 5.2, 5.3, 5.4_

- [ ] 3.3 (P) 監査用の要約ログ追記サービスを実装する
  - セッション単位でターンの要約を追記し、追跡可能な状態にする
  - 失敗時も交渉継続できるよう、記録処理の失敗は致命化しない
  - _Requirements: 7.1_

- [ ] 3.4 (P) 出力の安全化フィルタを実装する
  - 不適切または無関係な出力を検知し、交渉継続可能な安全な文に置換する
  - 置換したかどうかと理由を追跡できる形で返す
  - _Requirements: 7.2_

- [ ] 4. 非LLMの返答生成を実装する
- [ ] 4.1 (P) ルールベースで選手側の返答を生成できるようにする
  - 選手コンテキストを踏まえ、交渉を前に進める返答を生成する
  - 情報不足時は確認質問を返し、交渉の前提を埋められるようにする
  - _Requirements: 3.2, 4.4, 5.3, 5.4_

- [ ] 4.2 (P) ルールベース返答に交渉ステータスの遷移を反映できるようにする
  - 交渉継続/合意/決裂のいずれかを返答とともに決定できるようにする
  - 確定条件の最小ルールを定義し、誤判定を避けるガードを入れる
  - _Requirements: 2.3, 2.4_

- [ ] 5. LangChainによるLLM返答生成を実装する
- [ ] 5.1 LangChainで交渉返答をオーケストレーションできるようにする
  - 会話生成の入口を用意し、交渉ターンごとにモデルへ入力できるようにする
  - 選手の役割と口調を固定し、返答の一貫性を確保する
  - _Requirements: 4.1, 4.2_

- [ ] 5.2 LLM返答に会話履歴と選手コンテキストを反映する
  - 直近の会話履歴を入力として与え、過去の文脈を踏まえた返答を生成する
  - 選手情報コンテキストを利用し、納得感のある返答になるようにする
  - _Requirements: 4.3, 5.3_

- [ ] 5.3 LLM返答で確認質問と根拠提示を扱えるようにする
  - 情報不足時に確認質問を返す振る舞いを成立させる
  - 合意/決裂に影響する根拠をユーザーが理解できる形で返答に含める
  - _Requirements: 4.4, 4.5_

- [ ] 5.4 LLM失敗時にフォールバックし、交渉を継続できるようにする
  - 設定不備、タイムアウト、外部障害などの失敗を捕捉し、非LLM返答へ切り替える
  - 失敗の要約を監査ログへ記録できるようにする
  - _Requirements: 3.4, 7.1_

- [ ] 6. 返答生成の統合と状態更新を実装する
- [ ] 6.1 返答生成の選択（LLM/非LLM）を統合する
  - LLMの有効/無効設定に応じて返答生成経路を切り替える
  - LLM経路で失敗した場合に自動でフォールバックする
  - _Requirements: 3.2, 3.3, 3.4_

- [ ] 6.2 返答生成の出力を安全化し、セッション状態を更新する
  - 返答を安全化フィルタに通してから会話履歴へ反映する
  - 返答結果に応じて交渉ステータス（継続/合意/決裂）を更新する
  - _Requirements: 2.3, 2.4, 7.2_

- [ ] 7. サーバ側の交渉ターン処理を実装する
- [ ] 7.1 交渉開始と履歴取得のサーバ処理を追加する
  - 交渉開始時にセッションを作成し、初期状態を返せるようにする
  - 画面表示に必要な履歴とステータスを取得できるようにする
  - _Requirements: 1.1, 2.1_

- [ ] 7.2 ユーザー送信から選手応答までの1ターン処理を実装する
  - 入力検証を行い、空入力などは送信せずエラーを返す
  - ユーザーメッセージと選手メッセージを順序通り永続化し、更新後の履歴を返す
  - _Requirements: 1.2, 1.3, 1.5, 2.1, 2.2_

- [ ] 7.3 確定後の送信拒否と理由返却を実装する
  - 合意/決裂後は追加送信を拒否し、ユーザーに理由を返す
  - 同時送信などの競合でも一貫した振る舞いになるようにする
  - _Requirements: 2.5_

- [ ] 7.4 LLM設定の切り替えを反映できるようにする
  - 交渉中にLLM有効/無効を変更できる導線を提供する
  - 設定変更が以後の交渉セッションに反映されるようにする
  - _Requirements: 3.1, 3.5_

- [ ] 8. チャットUIを実装する
- [ ] 8.1 会話履歴の表示と送受信を実装する
  - 交渉開始時にチャット画面を表示し、履歴を読み込めるようにする
  - 送信したメッセージと選手応答を履歴に追加して表示する
  - _Requirements: 1.1, 1.2, 1.3_

- [ ] 8.2 交渉ステータスの表示と確定後の操作制御を実装する
  - 交渉ステータス（提案中/返答待ち/合意/決裂）を表示する
  - 確定後は入力や送信を無効化し、状態が分かるようにする
  - _Requirements: 1.4, 2.5_

- [ ] 8.3 入力検証とエラーメッセージ表示を実装する
  - 空入力などの不正入力をUI側で検知し、送信せずにエラーメッセージを表示する
  - サーバ側の検証エラーも分かりやすく表示する
  - _Requirements: 1.5_

- [ ] 8.4 返答生成中の処理中表示を実装する
  - 返答生成中にユーザーへ処理中状態が分かる表示を行う
  - 連続送信を防ぎ、状態遷移が破綻しないようにする
  - _Requirements: 7.3_

- [ ] 8.5 選手情報の要約表示をチャット画面に統合する
  - 交渉中に参照できる選手情報の要約を表示する
  - 情報取得に失敗した場合も、交渉継続可能な表示にする
  - _Requirements: 5.5, 5.4_

- [ ] 8.6 LLM有効/無効の切替UIを追加する
  - LLMの有効/無効を切り替えるUIを提供する
  - 変更後の挙動が分かるように表示上のフィードバックを行う
  - _Requirements: 3.1, 3.5_

- [ ] 9. 既存の契約フローから交渉チャットへ統合する
- [ ] 9.1 既存の契約体験を壊さずに交渉開始導線を追加する
  - 現在の契約画面から交渉チャットを開始できる導線を追加する
  - 選手選択やユーザー文脈と紐づけてセッションを開始できるようにする
  - _Requirements: 1.1_

- [ ] 9.2 交渉結果（合意/決裂）をUI上で分かる形に反映する
  - 合意/決裂の確定状態をUIに反映し、交渉が終わったことが明確に分かるようにする
  - _Requirements: 2.3, 2.4, 1.4_

- [ ] 10. テストで主要フローとフォールバックを検証する
- [ ] 10.1 (P) ドメインサービスのユニットテストを追加する
  - セッションの追記禁止、状態遷移、履歴取得の整合性を検証する
  - 選手コンテキスト取得の成功/失敗パスを検証する
  - _Requirements: 2.5, 5.4_

- [ ] 10.2 (P) 返答生成（非LLM/LLM/フォールバック）のテストを追加する
  - 非LLM返答の確認質問とステータス遷移の分岐を検証する
  - LLM失敗時にフォールバックされることを検証する
  - _Requirements: 3.2, 3.4, 4.4_

- [ ] 10.3 (P) 安全化フィルタと監査ログのテストを追加する
  - 不適切出力の置換が行われることを検証する
  - セッション単位の要約ログが追跡できることを検証する
  - _Requirements: 7.1, 7.2_

- [ ] 10.4 統合テストで1ターン処理とUI表示の一貫性を検証する
  - 送信→応答→履歴更新→ステータス表示までの一連を検証する
  - 空入力や確定後送信の拒否がUIに反映されることを検証する
  - _Requirements: 1.2, 1.3, 1.4, 1.5, 2.5_

- [ ]* 10.5 チャットUIの追加の受け入れテストを拡充する
  - 表示と操作の境界条件（スクロール、連続送信、エラー復帰など）を追加で検証する
  - _Requirements: 1.1, 7.3_
